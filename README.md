In rtnls_vascx_app, I want to set up a fully static PWA (progressive web app) to allow researchers to easily extract retinal vascular parameters using the retinalysis-vascx package (rtnls_vascx) and in the future maybe other packages. The PWA will be deployed in Github pages.

# Main goal
The app should be able to run the three stages of retinalysis-vascx processing completely in the browser:
Stage 1. Preprocessing - using rtnls_fundusprep - see rtnls_vascx/notebooks/0_preprocess.ipynb
Stage 2. AI inference - using ONNX version of the models used in rtnls_vascx/notebooks/1_segment_preprocessed.ipynb to run a similar pipeline.
Stage 3. Feature extraction - in the browser again - as done in rtnls_vascx/notebooks/2_feature_extraction.ipynb

# Architecture
The app should be developed in svelte5 + vite as a pure frontend application and compiled as a valid pwa using the Vite plugin.
- The preprocessing should be ran using Pyodide, importing a suitable version with compatible libraries (check requirements for rtnls_fundusprep).
- The AI inference stage should run using WebGPU via ONNX Runtime Web using GPU acceleration. The models should be downloaded from huggingface when the app loads:
- The feature extraction (rtnls_vascx) should run in Pyodide again. Make sure that vascX can run correctly in Pyodide regarding dependencies.

Use TypeScript/JavaScript as the orchestrator, with three workers:
Svelte UI
  │
  ├─ Pyodide worker: preprocessing
  │     └─ retinalysis-fundusprep
  │
  ├─ ONNX/WebGPU worker: inference
  │     └─ onnxruntime-web/webgpu
  │
  └─ Pyodide worker: feature extraction
        └─ retinalysis-vascx
The latest versions of Python packages retinalysis-fundusprep and retinalysis-vascx should be installed by the application via Pyodide. Implement stage 2, including windowing/TTA/postprocessing glue, in TypeScript, not inside Pyodide. Look at retinalysis-inference to understand how the windowing, TTA and postprocessing should be implemented.

# Interface / UX requirements
The app should have two main screens:

Screen 1. Single-image inference
Allows the user to "drop" an image into an upload box, or to click a button to upload an image. The image should go through the three stages in the browser, completely in memory. Spinners should be shown as the processing moves across stages. As stages complete, visualisations for each stage should be shown, each in a different section / card:
- The bounds image for the pre-processing stage, ie. the results of bounds.plot (rtnls_fundusprep/rtnls_fundusprep/cfi_bounds.py)
- The overlay for the AI inference stage (see rtnls_vascx/notebooks/1_segment_preprocessed.ipynb).
- The output biomarkers and visualisations for the feature extraction stage. This should be shown as a table with biomarker names and values for the current image. Next to each biomarker name / value, there should be a button to open the corresponding biomarker visualisation. The visualisations are the ones generated by the plot method of each biomarker. They should be generated on demand when the visualisation button is clicked. Keep the stage 3 worker alive and VascX retina for the current image loaded to make sure that plots are generated efficiently.

When the user loads another image, the previous Retina object in the stage 3 worker should be discarded and a new one created. Keep at most one Retina object in memory in the worker. The other workers should also be kept alive.

The layout of the page in screen 1 should be: one row above should show, from left to right: the uploaded image, the bounds image, and the overlay. Clicking any of these images should open a model to be able to look at them more closely. A second row below show show the biomarkers table. Clicking the visualisation button should open a modal window with the 1024x1024px visualisation.
All images should have a small download button in one corner. Any errors in image loading (eg. wrong format) or in processing should be handled gracefully with an error message. If any stage fails, the user should be prompted to report the error or try another image.

Screen 2. Batch inference
- The user must select and authorize the browser to use a source folder containing valid images. Optionally, the user can also select a segmentations folder to write intermediate segmentations and files. The input folder is expected to contain fundus images and the segmentations folder is expected to be empty. The app should perform a deep search of the input folder in search for valid image formats to be used.
- Before running, show a summary of the image files found in the source folder, and visualize some of them. Ask the user to confirm before preprocessing.
- Despite being called batch inference, this should run one image at a time. ie. each image should go through the three stages before moving on to the next.
- Show a clear progress bar. Also indicate the current image that is being processed and the processing time per image.
- Do not visualize individual outputs. Instead, just aggregate the outputs in memory.
- This mode should support resuming execution if the processing is interruped, but the same input folder is authorised in the next session. Use localStorage or a relevant store to keep track of the approved folder, the list of input images, and the currently computed biomarker outputs. A "Clear Results" button should allow for clearing this cache. if the cache is not clear, it should be possible to download the current set of outputs, or to select the same folder to resume execution. If a different folder is selected, the cache should be cleared and a new one created for the new folder, ie. dont keep multiple caches for multiple folders.

The layout: arrange the folder selection boxes in a row, with the source folder on the right and the segmentations folder on the right. Indicate the role of each folder, the valid image formats, and that the segmentations folder should be empty. When the source folder is selected, a dropdown below this first row should display the image samples and the total number of images found. An expandable box should show the complete list of images found. 

If the user attempts to leave this screen while batch processing is running, or without downloading the CSV file, show an alert for confirmation. The data will be lost if they leave.

If a segmentations folder is selected before execution, intermediate model segmentations should be written to this authorised folder. Otherwise, they should simply be kept in memory until stage 3 completes. The tabular data (eg. bounds, fovea, final biomarkers) should also be stored to this folder when execution completes.

## Other UX requirements
- Use shadcn-svelte as frontend library. Layout the site using a Navigation Menu at the very top. 
- Make the interface as clear as possible and provide clear instructions and specifications to the user. For example, what image folders are supported, what will the outputs look like, etc. Use tooltips and labels to label the interface.
- I should be able to switch between the two screens using a Sidebar component on the left. The main screen (on the right) should be different for the two modes as explained above.
- All the models and packages should be installed and loaded on initialisation of the app, and ideally cached. A loader should be shown indicating the progress loading the models.

## Other notes:
- The available feature_sets (vascx) should be bundled at build time to display them on the interface. The user should be able to pick amongst them.
- Be careful with memory during inference and feature extraction. Stage 2 should store model outputs after every batch. Only the tabular outputs (fovea) should be aggregated in memory. Stage 3 should run image-by-image, and keep biomarkers in memory.
- Do not implement CPU parallelism in any of the stages. I want a single CPU worker per stage to keep things simple.
- Propose changes to retinalysis-vascx if they make communication with the WPA more simple. For example, the interface for plot generation could be simplified.

## Browser support
ONNX runtime should be set up with WebGPU if available, otherwise default to WASM. Any browsers not supporting either are unsupported and a clear error message should be shown on load. Show a warning or notice if GPU acceleration is not available.
File System Access API should be the default for loading images for batch processing in Screen 2. However, it should only be required if the user attempts to pick a folder for segmentations. For input images, fall back to a multi file input element, where the user can manually pick images rather than a folder.

## GitHub Pages deployment

This app is configured for the public URL `https://eyened.github.io/retinalysis-vascx-app/`.

Deployment is handled by `.github/workflows/deploy-pages.yml`. In the GitHub repository settings, set Pages to deploy from GitHub Actions, then push to `main` or run the workflow manually.

The Vite base path is `/retinalysis-vascx-app/` during GitHub Actions builds. For local development it remains `/`, and it can be overridden with `VITE_BASE_PATH` when needed.
